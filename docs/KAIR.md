# Local competitive KAIR baseline

This implementation follows the competitive mode in Algorithm 3 of Song,
Chawla and Madisetti's [2026 journal paper](https://ieeexplore.ieee.org/stampPDF/getPDF.jsp?tp=&arnumber=11431212),
DOI [10.1109/TCSS.2026.3668728](https://doi.org/10.1109/TCSS.2026.3668728).
The journal text was retrieved and checked directly. The
[earlier preprint](https://arxiv.org/html/2503.13275v2#S3.SS3) describes the
competition principle, but does not contain the journal's Algorithm 3.

## Reference mapping

The paper has each agent solve the complete question with private known facts,
unresolved requirements and query history. Agents use identical prompts and
independent stochastic sampling. Each runs knowledge-aware query planning,
retrieval, knowledge updating and source-preserving context filtering. When a
candidate resolves all requirements, the competition returns that context.
Otherwise the candidate with the fewest unresolved requirements supplies the
shared context for the next competition iteration. The private knowledge bases
are not combined. These operations are preserved in this baseline.

| Reference operation | Implementation |
| --- | --- |
| Private K, R, Q and working context | `src/kair/state.py`: one fresh `KAIRState` per agent and question |
| Query planning using K/R/Q/context | `src/kair/agent.py`: `PLAN_PROMPT`; one validated new BM25 query |
| Knowledge update, K append / R replace | Source-backed candidates; retained old facts plus accepted new claims; full replacement requirement list |
| Binary fact checking | Separate accept/discard decision over candidate IDs and retained private fact IDs |
| Source-preserving filtering | Select original document IDs and sentence indices from available context; reconstruct exact text |
| Complete-candidate early stop | Stop subsequent scheduled agents when an initialized candidate has no remaining requirements |
| Best partial proposal | Select minimum requirement count without consulting gold labels |
| Shared refined context | Publish only the selected candidate's source sentences for the next iteration |

An initial empty R is not a solution: `initialized` remains false until a full
update/check/filter cycle succeeds, and completion also requires nonempty
accepted knowledge. This prevents an unstarted or failing agent from winning.

## Documented local adaptations

- **Serial execution:** one Ollama request at a time. Agents execute in order,
  with the starting agent rotated each competition iteration. The first complete
  candidate skips later scheduled work. This is not an asynchronous race or
  cancellation mechanism, and its runtime cannot reproduce the paper's scheduler.
- **Bounded launches:** each agent's KAIR launch runs at most two retrieval
  cycles per competition iteration. There are at most two iterations. Private
  memory persists between iterations. This makes the inner and outer budgets
  explicit; the paper does not prescribe these local limits.
- **Identical templates, independent sampling:** the agent IDs are trace metadata,
  not distinct role instructions. Agent seeds are the project seed plus the
  zero-based agent index (42 and 43 by default); every KAIR operation samples at
  temperature 0.7. Different seeds permit diversity but do not guarantee different
  queries. BM25 itself remains deterministic.
- **Retrieval environment:** the configured local Qwen model and HotpotQA dev
  distractor document pools replace the paper's model/retrieval environment.
  Retrieval is always enabled; there is no external router or gold-aware moderator.
- **Structured operations:** update emits at most four candidate claims and six
  requirements; a separate binary check decides admission, retention and the
  remaining requirements. Unsupported/contradicted old claims may be discarded.
  K/R/context commit together only after filtering passes all structural checks.
  Source sentences have explicit original index labels. Fact-check schemas limit
  each ID field to its actual private-known or proposed-candidate IDs; validators
  independently reject unknown IDs rather than repairing an invalid response.
  Candidate IDs are assigned by the program, not generated by the model.
  Multiple valid candidate citations to one document are combined by original
  sentence index; every citation is checked before combining and no text is rewritten.
  Since the 30 October maintenance review, the final context filter uses the
  same validated merge for repeated document selections. Update and filtering
  schemas restrict source IDs and sentence indices to the available context;
  empty context permits no new source claims. Parsers still reject unknown or
  unavailable references. See [the review](PROJECT_REVIEW.md) for validation
  and the distinction from the historical benchmark revision.
- **Failure handling:** malformed output, unknown IDs, invalid evidence or a
  failed generation retire that agent for this question. Healthy competitors
  continue. If no valid initialized proposal exists, the question is an error.
  Agent failures remain in traces and in the dataset summary even if another
  agent supplies an answer. No automatic retries or JSON repair are performed.
- **Stalled queries:** repeated queries stop that launch without another retrieval.
  A stalled agent is eligible to run in the next iteration with new shared
  context. If no agent is active and shared context has not changed, competition
  stops. The best valid partial candidate can still support synthesis or abstention.
- **Common answer generation:** the selected agent's accepted facts and remaining
  requirements go to the same final synthesizer, prompt, decoding policy and
  citation validator as RAIR. The journal instead evaluates a separate generator
  from refined context. This common local policy controls a potential comparison
  difference; it is not an exact reproduction of the journal QA setup.

Equal partial requirement counts use the current execution order as a tie-break.
Only the chosen source context becomes shared; other candidates' facts, requirement
lists and histories do not transfer. A recipient must independently extract and
check facts from shared source text before adding them to its own knowledge.

## Budgets and outputs

The configured maximum is `2 agents * 2 iterations * 2 steps = 8` retrievals,
with up to `4 * 8 + 1 = 33` LLM generation attempts. Each step performs planning,
knowledge updating, checking and filtering; the last call is common synthesis.
Early stopping and validation failures can reduce actual usage. Request timeouts,
context size and generation limits are the shared Ollama settings. These are
call/step budgets, not strict total-token or overall wall-clock limits.

Run from the project root:

```powershell
.\.venv\Scripts\python.exe -m src.experiments.check_kair_pipeline
.\.venv\Scripts\python.exe -m src.experiments.run_kair --limit 3
.\.venv\Scripts\python.exe -m unittest discover -s tests
```

`run_kair` supports the same `--config`, `--offset`, `--limit` and `--output`
arguments as RAIR. It uses the shared diagnostic writer. Metadata records the
model identity, dataset hash, settings, selected question IDs and budget/scheduler
policy. Finished questions are flushed to a new JSONL file; existing outputs are
never overwritten. Gold labels are used only for post-inference scoring.

Each result includes both private agent states, selection per iteration, incoming
and published source context, intermediate claims/checks, exact request/response
traces, selected agent, final sources and actual usage. Missing token counts are
flagged rather than estimated. Summary answer scores include all selected
questions, with errors/abstentions as empty predictions. It also counts agent
failures separately from question-level execution errors.

## Scope and remaining evaluation

This completes a runnable local competitive baseline. It does not prove either
system's superiority. Default maximum budgets differ from RAIR's five retrievals
and 22 LLM calls. A future comparison must freeze prompts, question splits, seeds,
budgets and metrics, measure actual usage, and account for the serial scheduler.

Fact checking, requirement completeness and sufficiency remain model judgments.
Source-index validation prevents invented source text, but cannot guarantee that
every accepted claim or final answer follows semantically from its evidence.
The three development diagnostic questions are not an untouched evaluation set.

## Step 2 validation: 18 October 2026

All 150 automated tests pass, including the 126 pre-existing tests and 24 new
KAIR competition/runner tests. The new coverage includes private-state isolation,
independent seeds with identical initial messages, partial-proposal selection,
winner-only context publication, retrying stalled launches after context sharing,
early completion, isolated agent failures, atomic memory commits, source-index
validation, gold-label mutation, output preservation and batch interruption.

The final local-model smoke check passed both cases with zero agent errors:

| Case | Outcome | Retrievals | LLM calls |
| --- | --- | --- | --- |
| Complete author-to-birthplace evidence | `Nerava`, cited evidence from both documents | 1 | 5 |
| Birthplace removed from source pool | Empty-answer abstention after both agents ran | 4 | 17 |

[Final smoke trace](../results/step2_kair_pipeline_20261018T131311159501Z.json).
The negative smoke case uses one competition iteration; its policy is recorded
inside the case. Test fixtures are created inside the project root when the
sandbox's default temporary directory is restricted.

Earlier development runs exposed candidate IDs being confused with existing
private fact IDs. Other runs exposed unnecessary model-generated candidate numbering
and split source citations. The final implementation assigns candidate IDs in code,
supplies explicit source sentence labels, constrains allowed IDs in the fact-check
schema, and independently validates the result. Failed earlier traces are retained.

The final three-question HotpotQA diagnostic completed with **zero agent errors
and zero question-level execution errors**. It used the final code and settings:

| Question | Final result | Exact match |
| --- | --- | --- |
| Scott Derrickson / Ed Wood nationality comparison | Abstention | 0 |
| Government position held by the actress in Kiss and Tell | `Shirley Temple` (wrong answer type; reference: `Chief of Protocol`) | 0 |
| Science fantasy series with alien-world companion books | `The Animorphs` (normalizes to `Animorphs`) | 1 |

Mean exact match and answer F1 were both **0.3333**, and answer coverage was
**0.6667** over all three questions.
[Final HotpotQA trace](../results/kair_20261018T131349340576Z.jsonl).

All three retrieval runs stopped when the selected agent reported no unresolved
requirements. Nevertheless, the common synthesizer abstained on one and answered
the wrong type on another. Model-assessed completion therefore does not establish
answer correctness. These development diagnostics demonstrate execution and expose
reasoning limitations; they are not a comparative benchmark or a claim that KAIR
outperforms RAIR. These are Step 2's historical results. The subsequent common
comparison is documented in [Step 3 evaluation](EVALUATION.md).
